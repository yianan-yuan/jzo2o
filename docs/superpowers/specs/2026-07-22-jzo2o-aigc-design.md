# jzo2o-aigc 家政 AI 助手设计

## 1. 背景

当前 AI 客服实现位于 `jzo2o-customer`，通过一个无状态接口调用本地 Ollama。请求只包含单条用户消息，响应只包含文本，不支持会话、需求澄清、真实服务推荐或业务数据校验。微信小程序中的 AI 页面直接使用硬编码地址调用旧接口，未复用统一请求封装；旧接口还位于网关免登录名单中。

本次改造将 AI 能力迁移到独立微服务 `jzo2o-aigc`。AI 助手作为家政客服，负责理解用户需求、推荐当前城市真实可售的家政服务，并引导用户进入现有详情和预约下单流程。

## 2. 目标

- 创建独立的 `jzo2o-aigc` 微服务，并接入现有 Nacos、网关、JWT 用户上下文、Feign、Redis 和日志链路。
- 支持短期多轮对话，在信息确实不足时进行针对性追问。
- 通过内部业务接口查询当前城市真实可售的服务。
- 以流式方式返回助手文本、处理状态和服务推荐卡片。
- 支持本地 Ollama，并可通过配置切换 OpenAI 兼容模型服务。
- 保留现有服务详情、预约、下单和支付流程。
- 迁移完成后删除 `jzo2o-customer` 中的旧 AI 后端实现和旧网关入口。

## 3. 非目标

首版不包含以下能力：

- AI 直接创建订单、选择优惠券、发起支付或修改交易数据。
- 历史会话列表、永久聊天记录或跨设备恢复会话。
- 向量数据库、文档知识库或 RAG。
- 读取用户地址簿、订单记录、支付信息或其他非必要个人数据。
- 语音对话、图片理解、人工客服转接后台或运营管理界面。
- 由模型自由调用任意微服务的自主 Agent。

## 4. 核心架构决策

采用受控推荐工作流，而不是自主工具调用 Agent。

模型只负责提取结构化需求、生成澄清问题、从服务端提供的有限候选中选择相关服务，以及生成面向用户的解释。后端负责控制流程、调用业务接口、校验模型输出并组装权威推荐卡片。

选择该方案的原因：

- 本地小模型也能完成范围明确的结构化任务。
- 服务 ID、名称、价格、单位和图片不会由模型生成。
- 调用次数、延迟和异常路径可预测、可测试。
- AI 服务无法突破订单和交易边界。

项目当前使用 Java 11 和 Spring Boot 2.7.10。首版使用轻量模型适配接口通过 HTTP 对接模型服务，避免为了 AI 集成而升级整个基础技术栈。

## 5. 服务边界

### 5.1 jzo2o-aigc

- 服务注册名：`jzo2o-aigc`
- 上下文路径：`/aigc`
- 数据存储：仅使用 Redis 保存短期会话，不建立业务 MySQL 库。
- 业务依赖：通过 `jzo2o-api` 中的 Feign 契约调用 `jzo2o-foundations`。
- 禁止依赖：订单创建、优惠券核销、交易和支付写接口。

内部组件分为：

1. **对话接口层**：创建会话、接收消息并输出 SSE 事件。
2. **会话管理器**：校验会话归属，保存需求状态和有限消息上下文。
3. **推荐编排器**：执行需求理解、澄清判断、服务查询、候选筛选和结果生成。
4. **业务工具层**：封装服务搜索及详情查询，只暴露允许 AI 使用的只读能力。
5. **模型适配层**：统一 Ollama 和 OpenAI 兼容服务的流式调用方式。
6. **安全与可观测组件**：限流、超时、输出校验、脱敏和阶段耗时记录。

### 5.2 jzo2o-foundations 与 jzo2o-api

复用基础服务现有搜索和详情业务逻辑，并在 `jzo2o-api` 中补充 AI 推荐所需的内部查询契约。内部查询至少支持：

- 根据 `cityCode`、可选服务类型和关键词查询可售服务。
- 根据服务 ID 批量或单个获取权威服务详情。

内部接口必须执行与现有消费者接口一致的区域和可售状态过滤。`jzo2o-aigc` 不直接访问基础服务数据库，也不复制服务目录。

### 5.3 jzo2o-gateway

- 新增 `/aigc/**` 到 `jzo2o-aigc` 的路由。
- 复用现有认证过滤器并传递用户上下文。
- `/aigc/**` 不加入免登录名单。
- 将 AI 路由读取超时配置为至少 100 秒，并确保代理层不缓冲 SSE 响应。
- 删除旧 `/customer/consumer/ai/chat` 免登录配置。

### 5.4 微信小程序

- 保留 AI 悬浮入口和聊天页面。
- 创建专用流式请求封装，复用统一 `baseUrl` 和登录令牌。
- 展示流式文本、处理状态、推荐卡片、错误状态和重试入口。
- 点击推荐卡片后，携带真实 `serveId` 进入现有服务详情/预约页面。
- 删除硬编码主机和旧 `/customer/consumer/ai/chat` 调用。

## 6. 会话设计

### 6.1 生命周期

- AI 助手只允许登录用户使用。
- 会话由服务端生成不可猜测的 `sessionId`，并绑定认证上下文中的 `userId`。
- Redis 键包含用户 ID 和会话 ID，例如 `AIGC:SESSION:{userId}:{sessionId}`。
- 会话闲置 30 分钟后过期，每次有效交互刷新过期时间。
- 每个会话最多保留最近 10 轮消息；更早内容折叠为结构化需求摘要。
- 用户点击“新对话”时创建新会话，旧会话等待自然过期。
- 首版不提供会话列表和会话恢复界面。

### 6.2 会话内容

会话至少保存：

- 当前 `cityCode`。
- 结构化 `DemandProfile`：需求摘要、意图关键词、服务类型提示、已确认约束和已澄清事实。
- 最近 10 轮必要消息。
- 最近一次推荐的服务 ID 列表，支持“第二个怎么样”等指代表达。
- 当前是否存在正在生成的任务。

当 `cityCode` 发生变化时，清除上一城市的候选和推荐 ID，并使用新城市重新查询；通用需求摘要可以保留。

## 7. API 与流式协议

### 7.1 创建会话

`POST /aigc/consumer/assistant/sessions`

响应包含：

- `sessionId`
- `expiresInSeconds`

欢迎语由小程序静态展示，不需要为创建会话调用模型。

### 7.2 发送消息

`POST /aigc/consumer/assistant/sessions/{sessionId}/messages`

请求字段：

- `message`：必填，去除首尾空白后长度为 1 至 1000 个字符。
- `cityCode`：必填，表示小程序当前选择的城市。

响应为 `Content-Type: text/event-stream;charset=UTF-8`。使用 HTTP Chunked 传输，事件数据采用 JSON。

事件类型：

- `status`：阶段值为 `UNDERSTANDING`、`SEARCHING_SERVICES` 或 `GENERATING`。
- `delta`：助手文本增量。
- `recommendations`：权威服务推荐卡片数组。
- `done`：成功终止事件，包含最终阶段 `CLARIFYING`、`RECOMMENDING` 或 `NO_MATCH`，以及可选的 `suggestedQuestions` 快捷追问数组。
- `error`：失败终止事件，包含稳定错误码、用户提示和 `retryable`。

每次流必须以 `done` 或 `error` 其中之一结束，不能同时发送两种终止事件。连接异常断开属于传输故障，客户端显示重试入口。

推荐卡片包含：

- `serveId`
- `serveItemName`
- `serveItemImg`
- `price`
- `priceUnit`
- `recommendationReason`
- 固定动作类型 `SERVICE_DETAIL`

除 `recommendationReason` 外的业务字段全部来自 `jzo2o-foundations` 的最新查询结果。

### 7.3 小程序分块处理

小程序使用 `uni.request` 的 `enableChunked` 和 `RequestTask.onChunkReceived`。专用封装必须：

- 返回或持有底层 `RequestTask`，支持页面退出时 `abort()`。
- 将 ArrayBuffer 增量解码为 UTF-8。
- 缓存不完整字节和不完整 SSE 事件，不能假设一个网络 chunk 对应一个事件。
- 只在解析出完整事件后更新页面状态。
- 保持普通 JSON 请求封装不变，避免影响现有业务接口。

## 8. 受控推荐工作流

每轮对话执行以下步骤：

1. **请求校验**：验证登录状态、会话归属、城市编码、消息长度、限流和并发状态。
2. **发送状态**：校验通过并建立流后立即发送 `UNDERSTANDING`。
3. **需求提取**：模型输出受 JSON Schema 约束的需求结构。
4. **输出校验**：解析失败时以 `temperature = 0` 重试一次；再次失败时使用安全的通用追问或进入降级搜索。
5. **澄清判断**：只有缺失信息会实质影响服务类型时才追问，每轮最多提出一个问题。需要澄清时发送 `GENERATING`，流式输出该问题并以 `done: CLARIFYING` 结束，不调用服务查询。
6. **服务查询**：信息足够时发送 `SEARCHING_SERVICES`，调用基础服务查询当前城市可售服务。
7. **候选裁剪**：服务端先执行状态和城市过滤，每轮最多向模型提供 20 个候选。
8. **模型选择**：模型只能从候选 ID 中选择相关项并生成推荐理由。
9. **服务端复核**：对模型选择与候选集合取交集，重新使用权威字段组装卡片。
10. **流式生成**：发送 `GENERATING`，流式输出说明文本，再发送推荐卡片。
11. **结束本轮**：更新 Redis 会话并发送唯一的 `done` 事件。

产品规则：

- 每轮最多追问一个问题。
- 每轮最多推荐 3 个服务。
- 每轮最多返回 3 条快捷追问，内容只能用于继续咨询或调整需求。
- “家里需要打扫”等已足以映射服务类型的表达不做无意义追问。
- 没有有效候选时返回 `NO_MATCH`，不生成虚假服务。
- 模型无法创建订单、指定价格、调用未授权工具或扩大查询范围。

## 9. 模型适配

定义与业务无关的模型适配接口，至少覆盖：

- 结构化需求提取。
- 候选服务选择。
- 流式文本生成。
- 取消、首输出超时、总超时和 token 用量返回。

首版提供：

- Ollama 适配器，作为默认本地模型实现。
- OpenAI 兼容适配器，通过配置切换。

提供方、基础地址、模型名、密钥、温度、最大输出 token 和超时从环境变量或私有 Nacos 配置读取。业务代码不得依赖具体模型名称或厂商响应结构。

## 10. 安全与隐私

- 单条消息最多 1000 个字符。
- 默认每用户每分钟最多 10 条消息，参数可通过 Nacos 调整。
- 同一会话同一时间最多一个生成任务，重复提交返回冲突错误。
- 总处理超时默认 90 秒；模型首个有效输出超时默认 30 秒。
- 用户 ID 只从认证上下文读取，不接受客户端传入。
- 用户输入、服务描述和模型输出全部视为不可信数据，不能覆盖系统规则。
- 电话、身份证、银行卡等敏感信息在日志中脱敏，并在发送云端模型前尽量屏蔽。
- 不主动读取或传输地址簿、订单、支付和优惠券数据。
- 日志不记录完整提示词、完整候选数据或原始聊天全文。
- 真实模型密钥和密码不得提交到 Git；非敏感示例配置沿用项目现有 `.gitignore` 规则。

## 11. 异常与降级

### 11.1 流建立前

认证失败、会话不存在或过期、参数错误、限流和并发冲突使用标准 HTTP 状态及项目业务错误格式返回。

### 11.2 流建立后

模型超时、模型响应解析失败、基础服务异常等通过 `error` 事件结束流。客户端必须清除加载状态并按 `retryable` 决定是否展示重试操作。

稳定错误码至少包括：

- `AIGC_SESSION_NOT_FOUND`
- `AIGC_SESSION_EXPIRED`
- `AIGC_GENERATION_CONFLICT`
- `AIGC_RATE_LIMITED`
- `AIGC_MODEL_UNAVAILABLE`
- `AIGC_MODEL_OUTPUT_INVALID`
- `AIGC_SERVICE_CATALOG_UNAVAILABLE`
- `AIGC_REQUEST_TIMEOUT`

### 11.3 降级规则

- 模型不可用时，以规范化后的原始消息执行一次基础服务关键词搜索；搜索返回非空结果时按业务接口原有顺序取前 3 个，使用固定模板返回真实服务卡片并标记为降级响应，否则返回 `AIGC_MODEL_UNAVAILABLE`。
- 基础服务不可用时不返回推荐卡片，也不让模型生成替代商品。
- 模型返回候选集合外的 ID 或无效结构时丢弃该结果。
- 模型选择校验后为空时返回 `NO_MATCH`。
- 用户中止请求时关闭流，并尽可能取消下游模型任务。

## 12. 可观测性

每轮记录以下结构化指标：

- 请求 ID 和匿名化用户标识。
- 模型提供方和模型名。
- 会话加载、需求提取、服务查询、首个文本增量和总处理耗时。
- 模型调用次数、重试次数、token 用量。
- 候选数量和最终推荐数量。
- 终止阶段、错误码和是否降级。

`status` 事件应在请求通过校验并建立流后立即发送。所有受控成功或失败请求必须在 90 秒内结束，不把与部署硬件强相关的模型首字延迟设为首版固定验收门槛。

## 13. 迁移与发布

实施和发布顺序：

1. 在 `jzo2o-api` 和 `jzo2o-foundations` 增加向后兼容的内部服务查询契约。
2. 新增并部署 `jzo2o-aigc`。
3. 增加网关路由、认证和流式传输配置。
4. 改造小程序 AI 页面和流式请求封装。
5. 验证完整新链路。
6. 删除 `jzo2o-customer` 中的旧 AI 实现。
7. 删除旧网关免登录路径并下线旧接口。

需要删除的旧后端职责包括：

- `AiChatController`
- `IAiChatService`
- `AiChatServiceImpl`
- `AiChatReqDTO`
- `AiChatResDTO`
- `AiChatProperties`
- 旧 `jzo2o.ai` 配置

最终不保留 `/customer/consumer/ai/chat` 的兼容转发。该迁移没有数据库变更；回滚通过恢复上一版服务、网关和小程序完成。

## 14. 测试策略

### 14.1 单元测试

- 需求状态合并和城市切换处理。
- 缺失信息判断和每轮单问题限制。
- 候选 ID 交集校验和权威字段覆盖。
- 会话归属、过期、限流和单任务并发。
- 模型输出 Schema 校验、一次重试和降级决策。

### 14.2 契约与集成测试

- 使用固定假模型验证模型适配契约，CI 不依赖真实 Ollama。
- 模拟基础服务正常、空结果、超时和异常。
- 验证服务字段不被模型输出覆盖。
- 验证提供方配置切换不影响业务层。

### 14.3 流协议测试

- 正常事件顺序和唯一终止事件。
- 一个事件跨多个 chunk。
- 多个事件位于一个 chunk。
- 中文 UTF-8 字符跨 chunk。
- 建流后错误、网络中断和客户端取消。

### 14.4 小程序联调测试

- 未登录跳转登录。
- 状态展示和增量文本追加。
- 重复发送保护和页面退出取消。
- 会话过期后创建新会话。
- 推荐卡片跳转现有服务详情页面。

## 15. 验收标准

1. “我想找保洁”可以返回当前城市真实保洁服务，不做无意义追问。
2. 模糊且会影响服务类型的需求每轮最多追问一个问题。
3. 精确需求最多返回 3 个真实服务，权威卡片字段与基础服务结果一致。
4. “第二个怎么样”可以结合上一轮推荐继续解释。
5. 当前城市没有匹配服务时返回 `NO_MATCH`，不虚构服务。
6. 要求模型忽略规则、伪造低价或直接下单时不会越权。
7. 未登录、跨用户访问、超长消息和超频请求被拦截。
8. 模型不可用但关键词明确匹配时返回模板化降级推荐。
9. 基础服务不可用时不返回推荐卡片，并正确结束流。
10. 点击推荐卡片进入现有详情/预约页面，原下单和支付流程不受影响。
11. `jzo2o-customer` 中不再存在 AI 后端实现，小程序不再调用旧接口。
12. 新增代码不提交真实模型密钥或密码；非敏感配置继续遵循现有仓库规则。
