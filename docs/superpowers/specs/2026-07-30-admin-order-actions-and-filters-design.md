# 管理端订单操作与筛选设计

## 目标

完成管理端“订单列表”的筛选、查看与退款操作，并消除列表已经显示数据时仍出现“订单列表加载失败”的误提示。

## 已确认的业务选择

- 退款复用现有订单取消/退款链路，不创建模拟退款状态。
- 管理端只提交订单 ID 和退款原因；服务端使用当前管理员身份并负责状态校验、订单取消和支付渠道退款。

## 列表加载与筛选

### 问题与原因

页面现在在 `onMounted` 和 `watchEffect` 中都调用列表接口。路由响应式更新会再次触发 `watchEffect`，造成并发、重复请求，其中任一次失败都会显示错误提示，即使另一请求已经成功渲染了列表。

### 设计

- 页面初始化只执行一次加载；仅在明确的搜索、重置、排序、分页或路由 ID 变化时重新请求。
- 请求状态由同一个 `fetchData` 维护，成功响应不显示错误；非成功响应和网络异常显示接口返回的真实错误信息。
- 搜索参数统一转换：空字符串不传给接口；日期范围为空时不传时间条件；搜索和重置都将分页恢复到第一页。
- 服务端继续把空手机号作为“未筛选”，而不是 `contacts_phone = ''`。

筛选字段及组合方式：

| 字段 | 参数 | 行为 |
| --- | --- | --- |
| 订单编号 | `id` | 精确匹配 |
| 客户电话 | `contactsPhone` | 精确匹配，空值忽略 |
| 下单时间 | `minCreateTime`、`maxCreateTime` | 闭区间筛选 |
| 订单状态 | `ordersStatus` | 精确匹配 |
| 支付状态 | `payStatus` | 精确匹配 |
| 退款状态 | `refundStatus` | 精确匹配 |

## 查看订单

- `查看` 保持进入现有详情路由 `/order/orderList/orderDetail/:id`。
- 补齐运营端聚合详情接口 `GET /operation/orders/aggregation/{id}`。
- 接口返回现有 `OperationOrdersDetailResDTO` 所需的数据：状态流转、订单和客户信息、支付信息、服务记录、退款记录和取消记录。
- 不存在的可选记录返回 `null`，详情页按现有条件隐藏对应卡片；订单不存在返回明确的业务错误。

## 退款订单

- 列表根据订单数据决定退款入口是否可用：仅“已支付且未退款”并且处于现有取消链路允许的订单状态时可点击。
- 用户填写退款原因并二次确认后，前端调用 `PUT /operation/orders/cancel`，提交 `id` 与 `cancelReason`。
- 控制器从登录上下文填充当前管理员 ID、名称和用户类型，再调用 `IOrdersManagerService.cancel`。
- 服务层是最终校验点：拒绝不存在、未支付、已退款和不可取消状态的订单；通过校验后复用既有取消策略和退款支付处理。
- 成功后关闭弹窗、提示操作成功并刷新当前页；失败时保留弹窗和原因，让用户修正或取消。

## 验证

- 为重复加载、筛选参数清理、详情路由/接口和退款接口/可用性写回归测试。
- 管理端运行静态测试和生产构建。
- 订单服务模块运行对应 Java 测试或由 Maven 编译验证。
- 手动验证：无筛选显示订单、六种筛选组合、查看详情、允许退款、拒绝退款各一条。

## 范围外

- 不修改支付渠道自身的退款实现。
- 不对已退款或不可取消订单强制退款。
- 不修改历史订单页面。
