# 管理端、服务人员与好评率派单设计

## 目标

将平台从“企业与个人并行调度、综合评分”调整为面向个人服务人员的“好评率优先”模式；管理端的入口、服务数据和区域调度配置都使用同一套评价数据。

## 范围与约束

- 不删除历史企业配置字段或数据库记录，避免旧区域配置无法读取；仅从当前管理端界面、请求载荷和新派单策略中移除企业概念。
- 好评率仅统计可展示的统一评价记录：好评数除以好评与差评总数。
- 没有有效评价的服务人员视为“暂无评价”，在好评率优先规则中排在已有评价的服务人员之后。
- 好评率相同的候选人按当前接单数由少到多、距离由近到远排序，确保派单稳定且可解释。
- 服务人员服务数据必须来自真实订单和服务记录，不再展示伪造的综合评分或空白占位数据。

## 管理端工作台

快捷入口中的“企业认证”改为“评价管理”，跳转至现有的原生评价管理路由。工作台的“用户分析”区域（标题、漏斗图、支付趋势图及对应前端请求）全部移除，其余经营与订单分析保持不变。

## 服务人员详情

基础信息中的“综合评分”改为“好评率”。页面通过评价服务按服务人员 ID 读取好评率、有效评价数和好评数：存在有效评价时显示百分比及统计口径；没有评价时显示“暂无评价”。

“服务数据”标签页以服务人员 ID 查询已由该人员完成的真实订单。每一行展示订单编号、服务名称、好评或差评、实付金额、服务完成时间、服务前图片、服务后图片，并可进入订单详情。接口查询不到时显示空状态，不把首页或通用占位数据当作服务记录。

## 区域调度配置

区域配置页面只保留个人服务人员的接单量限制、服务范围半径、抢单超时时间、轮询等待时间和派单规则。页面不再显示或提交企业接单量与企业服务范围字段。

派单规则文案调整为：距离优先、好评率优先、接单量优先。历史配置值中的原“评分优先”值继续兼容，并在界面上显示为“好评率优先”。

## 后端派单

调度服务新增按服务人员 ID 批量读取统一评价好评率的内部接口，避免在候选人循环中逐个远程查询。调度侧的评分优先策略改名为好评率优先策略，并使用该接口返回的数据排序：

1. 有有效评价的服务人员优先于暂无评价的服务人员。
2. 有效评价人员按好评率降序排列。
3. 同一好评率按当前接单数升序排列。
4. 仍相同则按距离升序排列。
5. 最终以服务人员 ID 升序作为确定性兜底。

接单量优先和距离优先策略不改变原有含义。评价查询异常时，调度不能中断：所有候选人按“暂无评价”处理，并继续使用接单量、距离和 ID 兜底排序，同时记录诊断日志。

## 数据与接口边界

评价记录继续存储在 `jzo2o-customer-all.evaluation_record`。消费者、服务人员和运营管理端读取同一张表；服务人员详情和调度模块通过明确的内部评价 API 读取汇总数据，而不直接跨库访问。

服务记录查询由订单管理服务负责：它按服务人员 ID 返回订单和服务凭证字段；管理端只负责分页、展示和空态处理。联系电话、订单状态等既有详情字段不在本次改动中回退。

## 错误处理

- 无服务记录：返回正常空分页，前端展示“暂无服务记录”。
- 无评价：返回 `ratedCount = 0` 和空好评率，前端展示“暂无评价”。
- 评价服务不可用：派单降级但不失败；管理端显示“暂时无法获取好评率”且不伪造百分比。
- 旧区域配置含企业字段：服务端读取时兼容，更新当前个人配置时不覆盖历史企业字段。

## 测试与验收

- 后端单元测试覆盖好评率计算、无评价排序、同率按接单量/距离/ID 的稳定排序，以及评价服务异常的降级排序。
- 订单管理服务测试覆盖按服务人员 ID 返回真实服务记录和空分页。
- 管理端单元测试覆盖快捷入口替换、用户分析移除、好评率显示和区域请求不包含企业字段。
- 人工验收：工作台不再出现企业认证和用户分析；服务人员详情能展示已完成订单；区域配置无企业字段；选择好评率优先后派单顺序符合规则。
